# PPCの同時刻対とキネマティックGPS L1 FLOAT

2026-10-21。全6走行をRustで処理し、静止モデルと移動モデルの各6実行を保存した。
同時刻対でのFLOAT出力は302から8,258へ増えたが、大きな位置外れが残る。
今回もPPCでのRTK・PPP同等性能の受け入れは未達。

## 実装と比較条件

EpochMatcherは1e-7秒以内の観測を1対1で対応付け、片側だけの全観測も返す。
両入力の末尾まで処理し、重複・逆行時刻と入力エラーを衛星局別に報告する。
欠測を時刻の書き換えや補間で埋めない。

RtkPositionMode::Kinematicは毎エポック、位置の共分散と位置/ambiguity間の
相互共分散を初期化し、継続中の単差ambiguity状態とその共分散を維持する。
位置平均は前回値を線形化の種にする。静止モードは従来の既定値のまま。
未使用の観測にあったGPS 1CのLLI・半サイクル・電源/スリップイベントは
observe_skipped_epochで保守的に次回の全アーク再初期化へ反映する。
この通知は数値状態や測定時刻を進めない。

静止用FIX政策は移動モデルを明示的なエラーで拒否し、履歴を変更しない。
移動時のFIX政策は未実装であり、今回の出力にFIXはない。

比較は同じGPS 1C入力と既定の測定雑音・閾値を使用し、位置モードだけを変えた。
入力、ソース、バイナリ、基準局座標、評価仮定を
[predeclared-inputs.json](predeclared-inputs.json)へ保存してから12実行を開始した。
基準局はPPCのトップREADMEにある測量済み位相中心座標を用い、
移動局の初期値はRINEXヘッダーから読む。reference.csvはソルバーに渡していない。
補正・閾値を結果に合わせて調整していない。

基準局1 Hzと移動局5 Hzの同時刻対だけを測位する。5 Hz対応を示す結果ではない。
GPS以外の混合航法は明示的な選択APIで別保持する。
比較元のC++ RTKProcessor全体は今回実行しておらず、
ここでの「静止モデル」は従来のRustモデルを指す。

## 全走行の結果

全12実行が終了コード0。各モードで移動局58,634、基準局11,746エポックを処理し、
同時刻11,733対、移動局だけ46,901、基準局だけ13をすべて出力した。
エポックの台帳は両モードで一致する。未使用の観測中の継続性通知は計1,223件。

移動モデルは全同時刻対の70.4%、元の移動局5 Hz全エポックの14.1%でFLOATを出した。

## 位置の参考誤差

ユーザーの指定どおり、reference.csvをGNSSアンテナ位置とみなす仮定と、
IMU位置とみなしてレバーアームを加える仮定を両方保存した。
Tokyoのトップ/都市READMEはレバーアームが矛盾するため、その両方を評価した。
どれかを誤差に応じて採用する処理はない。座標を両ソルバー間で比較した結果でもない。

以下は「reference.csvがアンテナ位置」の仮定で、移動モデルの全FLOAT出力を
対応する真値と照合した値。全8,258出力で真値が見つかった。
FLOAT出力がある時刻だけの位置誤差であり、出力率は上表と合わせて評価する。

| 走行 | 水平RMS m | 鉛直RMS m | 水平P95 m | 最大3次元誤差 m |
| --- | ---: | ---: | ---: | ---: |
| nagoya-run1 | 2.102 | 7.280 | 3.388 | 99.155 |
| nagoya-run2 | 25.083 | 122.567 | 64.448 | 937.912 |
| nagoya-run3 | 13.092 | 17.586 | 30.262 | 109.137 |
| tokyo-run1 | 11.109 | 20.907 | 24.946 | 208.317 |
| tokyo-run2 | 4.735 | 6.644 | 13.468 | 48.475 |
| tokyo-run3 | 9.868 | 17.441 | 14.816 | 189.910 |

IMU仮定でも大きな外れは残る。出力数の増加を精度改善や実用同等性能とは扱わない。
静止/移動モデルでは成功時刻が異なり、両者の出力上のRMSを直接比較して
優劣を判断できない。次は外れ値と弱い幾何・未検出スリップ・モデル不足の関係を調べる。

## 独立した合成検証

新しいC++生成器は、固定したlibgnss++の放送暦・幾何・対流圏部品を使い、
ENU速度(1.2, -0.8, 0.1) m/sで1秒間隔・64エポックの既知軌道を生成する。
元の静止fixtureは変更していない。元のC++全RTKソルバーの出力を生成したものではない。
雑音なし/ありとも全64エポックがFLOATとなり、最大3次元位置誤差はそれぞれ
0.001074832 m / 0.085200681 m。既存の雑音条件と同じ3 mm /15 cmの上限を使用した。
静止モデルでは両条件とも63/64エポックで棄却または15 cm超のずれとなる。
共分散の正定値とアーク継続も確認した。

固定した元ソース2,091ファイルを元アーカイブと照合し、
新しい5 fixtureを再生成して完全一致を確認した。
SHA-256と生成結果は [native-moving-generation.json](native-moving-generation.json)。
追加6テストを含めRust272（docを含む）、examples、fmt、全ターゲットclippy、
releaseが通過した。証拠は [qualification.json](qualification.json) と圧縮ログ。

## 再実行

~~~bash
source /workspace/.cloud-setup/activate.sh
cargo build --release --locked --offline -j2 --example ppc_rtk_float
python3 -B scripts/run_ppc_rtk_float.py \
  --dataset-root /workspace/.cloud-setup/datasets/PPC-Dataset \
  --binary target/release/examples/ppc_rtk_float \
  --output-dir /tmp/new-ppc-kinematic-float
~~~

出力先には新しいディレクトリが必要。保存したCSVとテスト記録だけの検証は次で行う。
ソルバーやネットワークは実行しない。

~~~bash
python3 -B docs/comparison/2026-10-21-ppc-kinematic-float/verify.py
~~~

同じ検証器に --dataset-root を指定すると、参考位置誤差も再計算する。
PPCでのRTK・PPP同等性能は未達。確認済みチェックリストは18/24（75%）のまま。
